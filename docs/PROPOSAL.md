# MusicCraft · 下周提案内容

## 一句话与本期范围

用自然语言、原歌曲与参考声音驱动音乐编辑 Agent，完成**整体风格改编**与**个人音色翻唱**。从零作曲暂缓，精确单乐器替换不列入最低交付。

典型要求：「把这首古风歌改成木吉他流行编曲，尽量保留旋律」；「保留原来的伴奏和旋律，用组员上传的声音唱」。

## 体系与 LLM 的作用

LLM 将用户指令转换成结构化 TaskSpec：任务、目标风格、乐器、起点、时长、保留要求与资产。后端验证参数、发现冲突，再由显式工作流调用工具。风格路线用 ACE-Step Cover；歌声路线用 Demucs → Seed-VC → FFmpeg。结果、事件、父子关系与中间音轨保存在本地。

LLM 不生成波形；研究贡献应聚焦意图解析、约束保持与工具选择。当前界面默认规则解析，LLM 适配器已提供但尚未真实联调。

## 当前进展与下一步

- 已实现并本地验证：上传、方案确认、异步执行、版本与收藏回放、音频试听、错误处理。
- 已实现执行代码并用模拟模型验证协议：ACE-Step 适配器、异步歌声 Worker、分离/转换/混音命令、取消与分轨下载。
- 待完成：租用 GPU、安装模型、真实样例听测、LLM 供应商联调、实验与性能数据。
- 默认演示音频为合成占位，不能作为模型效果证据。

## 研究问题与评估

结构化约束和工具路由，是否能提高连续编辑中的指令遵循与内容保留？

先做可控、可复现的实验：直接提示调用固定工具，与 LLM 结构化解析后调用同一工具对比。使用相同源片段、种子、生成次数，避免把模型能力差异误认为 Agent 改进。

建议 12–20 条单轮任务覆盖两条路线，再做 5 组连续编辑。三名组员盲听、随机顺序评分：目标风格、旋律保留、歌词保留、音色相似、音质（各 1–5）；同时记录任务成功率、端到端耗时、人工修正次数。每个音频先检查文件与时长，再做听感评价；信号指标不代表语义质量。

## 六人分工与四周安排

| 人员 | 负责 | 最先交付 |
| --- | --- | --- |
| A | LLM 规划与约束 | 任务 JSON、冲突规则、真实 LLM 接入 |
| B | ACE-Step 部署 | 10–20 秒 Cover 成功样例 |
| C | 改编参数与数据 | 同一原曲的两个风格、强度对照 |
| D | 歌声管线 | 一名组员音色转换与分轨听测 |
| E | 前后端集成 | 两条路线、演示台、失败恢复 |
| F | 实验与报告 | 盲听协议、评分数据、失败例 |

第一周：proposal、租用环境、先证明两项音频能力可行。第二周：真实端到端联调、准备演示样例。第三周：LLM 规划对照实验、多轮约束。第四周：冻结功能、整理数据、彩排与报告。

如果首周真实效果不足，缩小到单人独唱、简单伴奏、10–20 秒片段；优先改善两项主功能，保留失败分析。作曲不占核心排期。
